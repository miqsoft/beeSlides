---
name: build-deck
description: Plan and build a deck from a topic or source material — outline first, then a slide type per slide, then the slides.
---

Build the deck the user asked for. Work in this order and keep the user informed in one short line per phase.

1. **Look at what exists.** Call `doc_info` (title, size, theme, slideTypes) and `outline` (one row per slide). Read the "Make a GREAT deck" section of the guide once: `read_reference("agents.md")` — skip it if you already know it.
2. **Outline before slides.** Write a numbered outline in chat: one line per slide with its message and the content kind (numbers → chart, comparison grid → table, same subject changing → morph pair, drill-down → state slide, hero image → ken-burns, headline number → count-up, concepts/features/steps side by side → an icon per item). Keep it to what the material supports; no filler slides. If the request is ambiguous about audience or length, state the assumption you made instead of asking.
3. **Set the look once, deck-wide, before building slides.** The look comes from, in this order: what the user asked for, the deck's own look (a template, slide types of its own, a theme someone set), else YOU choose one. A new deck on the plain default theme has no look yet: then decide an art direction and write it in chat in three lines — a palette (background, text, one or two accents; dark or light), a type treatment (system or embedded fonts; weight and size contrast, letter-spacing, an uppercase label style), and ONE signature motif that recurs on every slide (a shape, a band, a big numeral, an outline drawing of the subject). Aim for a deck a design studio would present, not a template. Apply it with `deck_settings` `{op:"theme"}` (colours, fonts) so the slides can use the theme variables; set `{op:"size"}` if asked.
   **Pick a slide type per slide.** Use the deck's own slide types from `doc_info` (`slideTypes`) and `list_reusable_objects`; when the deck has a look of its own, do not invent another. A slide whose purpose has no fitting type may use a new one: `create_slide_type` (mode `parent` or `basis` from an existing type), then `slide_type` `relink` to make a deck slide follow it. Slides that follow a slide type get its placeholders by `role`. `doc_info` `slideTypes` lists each type's `placeholders` (id, role, frame) and `contentArea` (the free space below its header and above its footer), so no probe slide is needed to find out where content goes.
4. **Create, then fill the slides.** Add every slide the outline needs in ONE call before filling any: `deck` `{op:"add", after, slideType, count, names}` returns the new ids in order (reuse empty placeholder slides that `outline` already lists first). Delete leftover empty slides you added with `deck` `{op:"delete"}`; never delete the user's slides unless they asked.
   - **If the `execute` tool is available (Code Mode)**, do this whole step as one `execute` program (a few for a long deck) instead of one call per slide: add the slides, write each one's HTML from shared functions, set notes, transitions and each slide's animations, and return the ids and warnings. The deck API is in the beeslides server's instructions; `api_search` only for what they leave out. The rules below still apply inside the program.
   - **Write each new slide as HTML**: `slide_html` `{op:"write", slideId, html, css}`. Lay it out with ordinary CSS (flexbox, grid, padding, gap) — the app lays it out in the browser and turns every box into an element, so you never compute a frame. On a slide that follows a slide type, fill its placeholders by giving your elements their ids and placing them at the placeholder's frame (`#<id>{position:absolute; left:<x>px; top:<y>px; width:<w>px}` keeps the template's look), and lay the rest out inside its `contentArea`; otherwise keep content inside the 96px side margins (`var(--bs-margin)`); keep to the deck's palette and at most two typefaces, and a whole text element in one typeface (a word in another face needs its own element). Effects carry over: soft glows (`filter:blur` or a radial gradient fading out), frosted glass (`backdrop-filter`), gradient text, `mix-blend-mode`, `clip-path` polygons, `::before`/`::after`, inline `<svg>` drawings for decoration (never for icons); repeating patterns, masks and scale transforms do not — the result lists anything it left out, so read it. Give every element an `id`; the same `id` on the next slide plus `transition:"morph"` morphs. Diagrams are components — `<div id data-component="steps|sequence|cards|compare|flow">` with the data as JSON (`slide_html` `op:"help"`): far fewer tokens than hand-made boxes and arrows, the deck's colours, and `data-active` / `data-show` step through them slide by slide (with `transition:"morph"`). Tables are `<table>`, charts `<div data-chart='{"preset":"bar","option":{…}}'>`, code `<pre>`, pictures `<img src="data:…">`; `op:"help"` lists the rest.
   - Animations: set a slide's `fx` in ONE `elements` `{op:"edit", changes:[{id, fx}, …]}` call, not one `update_element` per element.
   - Changes: small ones with `update_element` / `elements`; to restructure a slide, `slide_html` `{op:"read"}`, edit the HTML, write it back (ids keep animations and links).
   - Icons: `icons` `{op:"search", query}` with one short noun per concept, then `{op:"insert", slideId, ref, x, y, size}`; one size for every icon on a slide. Never draw icon SVG yourself; if the library is not set up, say so in the report and use simple shapes.
   - Put speaker notes on each slide with `deck` `{op:"notes", slideId, text}`; set transitions and sections with `deck` too (`op:"help"` lists the ops).
5. **Audit.** For every slide call `review_slide` once, fix what the screenshot or the layout findings show with the smallest verb (at most 2 polish rounds per slide), then `validate` once for the whole deck. Walk the self-audit checklist at the end of the "Make a GREAT deck" section.
6. **Report** in two or three lines: what was built, what was left for the user (missing images, anything `deck` help lists as not available yet), nothing else.

## Larger decks: plan once, write in parallel

When more than about 5 slides need filling and you can start subagents (`task` in the built-in chat, the Agent tool in Claude Code — writers can run on a faster model, e.g. sonnet), split the writing; the time a deck takes is mostly the writing, and writers work at the same time.

1. **You plan and prove the look.** Steps 1–3 as above, then add every slide in one `deck` `add` call. Write the FIRST content slide yourself and `review_slide` it once: it is the reference every writer copies (title placement, `contentArea`, component choices, font sizes, colours).
2. **Hand out disjoint batches of 2–3 slides** (one each only if the user asks), all subagents started in ONE message so they run together. Each prompt is self-contained — a subagent knows nothing else:
   - the slide ids it owns and their outline rows (message, content kind, component);
   - the reference slide's HTML and CSS (from `slide_html` `read`), and: "copy its title placement and spacing; lay content out in the slide type's contentArea [x,y,w,h]";
   - the rules: write each slide with `slide_html` — or, if the `execute` tool exists, ONE program for all its slides; diagrams as `data-component` (steps, sequence, cards, compare, flow); ids unique per slide, the same id on consecutive slides for morph; speaker notes with `deck` `notes`; animations in one `elements` `edit` per slide; never add, move or delete slides;
   - then `review_slide` each of its slides once and fix with the smallest verb (at most 2 rounds);
   - "if a write answers that a program is running on this deck, wait a moment and do it again";
   - "answer with ONE line per slide: id — done, or what is left".
3. **You finish:** read the one-line answers, run `validate` once for the whole deck, delete leftover empty slides you added, and report. Do not re-review slides a writer already reviewed unless its line says something is left.
