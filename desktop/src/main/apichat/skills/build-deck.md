---
name: build-deck
description: Plan and build a new deck (or a run of new slides) from a topic or source material — profile, outline, a look the user picks, one deck stylesheet, a reference slide, then the slides written as one document with diagrams drawn for the content (big decks in parallel), a check, and alternatives for the slides where a choice matters.
---

Build the deck the user asked for, step by step, telling the user in one short line what each step is doing. For a new look on an existing deck use restyle-deck, to clean one up polish-deck, for one slide slide-designs.

**Questions.** By default, ask where a step says so: with your question tool if you have one (AskUserQuestion in Claude Code: up to 4 questions per call, 2–4 options each, your proposal first and marked "(Recommended)"; the user can always type their own answer), else in one message with a proposal for each point. When the user wants no questions ("just do it", "no questions") or nobody can answer, ask nothing and wait for nothing: take your proposals, say them in one line at the start and again in the report.

1. **Start.** Outside the app, when the user names a deck file or none is open, `open_deck` it (`create:true` makes a new one). Then `doc_info`, `outline`, and the design rules once: `read_reference("design.md")`.

2. **Profile.** Use `doc_info` `designRules.profile` when it is there; for slides added to a deck with content, read it off the deck. For a new deck, ask once, proposing an answer to each point from the request (with a question tool: the four that matter most, usually purpose, length, typical slide, and decoration with motion; the rest as assumptions beside them):
   - purpose: conference talk · lecture · meeting · pitch · for reading;
   - length: minutes → slides (about 1 per minute for a talk, 0.5 for a lecture or meeting), plus backup slides; for reading, a slide count;
   - typical slide: mostly text · text + small visual · balanced · visual + one-line takeaway · visual only;
   - visuals the user has (figures, photos to attach); decoration: plain (the default for a talk) · icons from the user's library · icons drawn for this deck (its own icon set, in its look) · imagery;
   - content that needs its own slide type: equations, code, tables, timeline, quotes, references;
   - motion: none · subtle (fades, morph) · expressive;
   - simplicity: minimal · clean · rich;
   - a look to follow: a template or .pptx, or none.

   The profile sets tone and budgets as design.md's "Tone and density" says.

3. **Outline.** A numbered outline in chat, grouped by section, one row per slide: its message (the one sentence the audience takes away; it becomes the title or takeaway), its evidence kind and its material (which figure, which numbers). Evidence kinds: title · section · closing · statement (one sentence, big) · one-result (one figure + takeaway) · comparison (two side by side) · detail (a figure with callouts) · overview (3–4 small multiples) · number (one figure beside what it is compared with) · process (steps / flow / sequence) · table · list (3–5 points) · equation · code · quote. Choose the kind from what the slide must show. Slides showing the same kind of thing share one kind on purpose (they read as a series and morph); unrelated slides of one kind stay at 3 in a row. Keep to what the material supports. A summary or recap row gets evidence too (the mechanisms side by side, a problem → fix table), not a list of headings. Where the form is open (a table or a chart, one figure or small multiples, a diagram or a list), write both in the row, your pick first, in at most 3 rows. With icon decoration, add one line after the outline: the icon concepts, one short noun each ("evidence bag", not "slide 4 icon") with the slides that use it; one concept is one icon everywhere. Over 10 slides, wait for the user's OK ("Outline OK?").

4. **The look.** It comes from what the user asked for, else the deck's own look (a template, its slide types, a theme someone set): keep it, reuse its slide types and add only the kinds it lacks, as children of its parent type. A deck without a look of its own (over 5 slides) gets one the user picks:
   - Write the outline's most typical content slide in 2–3 looks with ONE `propose_variants` call on it (add the slide, or reuse the deck's empty first slide; it stays and becomes that outline row).
   - Each look is a complete design in the sense of design.md "The look": a type pairing with jobs, a type scale, a motif on the slide (the header strip, the section kicker), colours with fixed meanings, and the evidence drawn for this content. Start from the starter looks in design.md that fit the profile, or make your own in that spirit. Give each design its `theme`, so its diagrams show in its colours and picking it sets the deck theme, and write its CSS on the theme variables.
   - Then do what the result says (outside the app: `variants` `{op:"previews"}` for the BeeSlides pane), and with a question tool also ask "Which look?", one option per design. Learn the pick from `variants` `{op:"status"}`; an answer that status does not show yet, apply with `variants` `{op:"pick", slideId, index}`.

   Without questions, build one look closest to the profile.

5. **The deck stylesheet.** One stylesheet for the whole deck, grown from the picked look (`slide_html` `{op:"read"}` on that slide gives its CSS): the type scale as classes (title, lead, text, label, kicker), the motif (header strip with the deck or section name and `{{page}}`), the colour meanings, and the diagram styles (labels, strokes, arrowheads). Say the type scale and what each colour means in one line in chat. Set the theme with `deck_settings` `{op:"theme"}` unless a picked look already set it; `{op:"size"}` if asked. Every slide is written with this stylesheet and only its classes, so the deck reads as one design.

   Slide types only when the user asks for a template, or wants to add slides in the app later in the same style: a parent type "Base" (`create_slide_type` mode blank, then `slide_html` on it) with the strip and the title as placeholders (`elements` `{op:"edit", slideId:<type id>, changes:[{id:"title", placeholder:"Title", html:""}, …]}`), one child per evidence kind (`create_slide_type` mode parent). `doc_info` then lists every type's `placeholders` and `contentArea`; fill a placeholder by giving your element its id at the placeholder's frame.

6. **Write the slides as one document.** Add every slide the outline needs in ONE call before filling any: `deck` `{op:"add", after, count, names}` (with slide types, one call per run of slides sharing a type), reusing the empty slides `outline` already lists. Write the first content slide and `review_slide` it: it is the reference the others follow. Then write the rest with `slide_html` `{op:"write", css:<the deck stylesheet>, slides:[{slideId, html}, …]}`, up to 6 slides per call (more than 6 left: writers, below). Over 10 slides, point the user to the reference slide (in the app, or in the BeeSlides pane outside it) and wait for their OK first.
   - The title slide is the cover (design.md "The look" 6): the key word huge, the title and a one-line promise, and a small motif drawn from the content. Write it with the first batch, not last.
   - Each slide: the motif, the section kicker where the deck has sections, the title claim, and one piece of evidence starting about 48px under the title and filling the area below it. Give every element an `id`; the same id on the next slide plus `transition:"morph"` morphs it (motion subtle or expressive).
   - Evidence: a mechanism, a process over time, a structure with parts is an inline `<svg>` drawn for this content (arrows with `marker-end` arrowheads, the deck's colour meanings); it becomes editable shapes. Make it explain (design.md "Evidence" 17): every state and part named, every arrow labelled with what it carries, one or two annotations at the point where something happens, every case the title promises. Standard steps, a sequence that reveals message by message, cards, a comparison or a flow can be a component: `<div id data-component="steps|sequence|cards|compare|flow">` with the data as JSON (`slide_html` `op:"help"`). Tables are `<table>`, charts `<div data-chart='{"preset":"bar","option":{…}}'>`, code `<pre>`. The result lists anything it left out.
   - With the `execute` tool (Code Mode), write your slides as one program from shared functions; the same rules apply inside it.

7. **Finishing touches.**
   - Animations, within the profile's motion: one `elements` `{op:"edit"}` per slide carrying every `fx`.
   - Icons, with icon decoration only: from the library, `icons` `{op:"search"}` with one short noun per concept, then `{op:"insert"}`; one size per slide. Without an icon library, say so in the report. Icons drawn for this deck: the section below, then insert them the same way from the set.
   - A figure the user has not supplied: a marked placeholder box ("Figure: <what it shows>") in its slot, never a chart of made-up numbers.
   - Speaker notes on every slide with `deck` `{op:"notes"}`.

8. **Check.** Look at every slide you wrote once with `review_slide` (not the reference slide again, unless it changed; slides a writer reviewed only if its line says something is left) and fix what it shows with the smallest tool: a small change is an `elements` edit, whose result already reports the layout check, so it needs no new screenshot; a slide wrong as a whole is written again with `slide_html` and the deck stylesheet, and looked at once more. At most 2 rounds per slide: every screenshot stays in the conversation and is paid for again on every later step. Every content slide puts the strip, kicker and title at the same place. A `layout-empty-band` finding is fixed, not accepted: move the evidence up or grow it (rewrite the slide with more room for the diagram). With 8 or more slides, start the critic (below) and fix the slides it names. Run `validate` once and delete empty slides you added (`deck` `{op:"delete"}`; the user's own slides only when they asked).

9. **Alternatives where a choice matters.** Name up to 4 slides where another design is most likely better (the main result, the critic's weakest) and offer them in one line. On a yes, one slide at a time: ONE `propose_variants` call holding the current form arranged differently, the other evidence form (table ↔ chart, diagram ↔ list, one figure ↔ small multiples) and the simplest version that still carries the point; keep the content, the deck stylesheet, the strip and title, and the ids of elements that stay. Learn the pick as in step 4, then offer the same treatment to slides of the same kind. Without questions, name the slides in the report instead.

10. **Report** in two or three lines: what you built, the profile in one line, and what is left for the user (figures to drop in, anything `deck` help lists as not available yet).

## Icons drawn for this deck

With decoration "icons drawn for this deck" the deck gets its own icons, drawn in its look and kept in an icon set file next to it. Do this after the slides are written (step 6) and before step 7's icons, never while writers are still at work: the tools work on one open file at a time for you and your subagents together.

1. **Library first.** `icons` `{op:"search", query}` per concept from the outline; a hit that fits the look is used as it is (skip this when the user wants every icon in one hand). The rest are drawn.
2. **The set.** Outside the app: an icon set the user names, else `<deck name>.icons.beeslides.html` next to the deck (reused when it is there): `open_deck` `{path, create:true, kind:"iconset"}`, then `doc_info`. Inside the app there is no `open_deck`: ask the user to make one (File ▸ New Icon Set…, saved next to the deck) and to draw it there (Plan with AI, Draw with AI), then go on with step 6 below.
3. **Its look comes from the deck.** In a new or empty set, ONE `icons` `{op:"plan", icons:[{name, prompt, keywords}, …]}` writes the icons to draw and how the set is drawn: `brief` (what the deck is about and how its icons look, in a line or two), `strokeWidth` (about the weight of the deck's text: 1.5 for a light, thin type, 2 regular, 2.5 bold), `cap` and `join` (round for a soft look, butt and miter for a technical one), `iconFill` (outline unless the deck is bold and flat: solid). The set's ink stays black: the deck colours it when the icons go in. A set that already has drawings keeps its drawing style: plan only the missing icons and give it a style for this deck instead (`icons` `{op:"style", name:"<deck name>", weight, …}`, only what differs, nothing redrawn).
4. **Show the plan** (the names and what each shows) and wait for the user's OK; without questions, go on and list it in the report.
5. **Draw** with the draw-icons skill, its subagents included (3 or more icons). They work on the set as you left it open: they never call `open_deck`, and you wait until all are back. Look at a few with `review_slide`.
6. **Back to the deck.** `open_deck` the deck again (the set stays open; nothing is lost), then `icons` `{op:"search", query:"", set:"<the set file>"}` lists the set's drawn icons as refs and its styles; `{op:"insert", slideId, ref, x, y, size, style?}` puts one on a slide. The ink becomes the deck's accent colour (`ink:"text"` or a hex for another), a style for this deck goes in with `style`. One size per slide; check them with `review_slide`.

## Writers: plan once, write in parallel

When more than 6 slides are left after the reference and you can start subagents (`task` in the built-in chat, the Agent tool in Claude Code; writers can run on a faster model such as sonnet), split the writing: writers work at the same time.

- **Batches are consecutive runs** of 2–4 slides, ideally one section each, so morph pairs and series stay with one writer. Start every writer in ONE message.
- **Each prompt is self-contained.** Fill in this block, leaving nothing out:

  > You are writing slides <ids> of an open slide deck (title <title>, size <w>x<h>). First read the design rules: <how you read design.md: `read_reference("design.md")`, or its path in the plugin>. Profile: <one line: purpose, typical slide, simplicity, decoration, motion>. The deck stylesheet, used for every slide and not to be changed: <the CSS>. Type scale and colour meanings: <one line>. The reference slide, whose strip, kicker, title placement and evidence style you follow: <its HTML>. Your slides, in order: <id — section — message — evidence and material>. Write them with ONE `slide_html` `{op:"write", css:<the deck stylesheet>, slides:[{slideId, html}, …]}` call (with the `execute` tool, one program). Draw mechanisms and processes as inline `<svg>` for this content, with the deck's colour meanings, every state and arrow named and one annotation where something happens; evidence starts about 48px under the title and fills the area below it; a standard diagram may be a `data-component`; ids unique per slide, the same id on consecutive slides for morph<, only if motion allows it>; a missing figure is a marked placeholder box. Keep to the design rules' budgets for <simplicity>, with the detail in the speaker notes (`deck` notes); over budget, tell me instead of shrinking the type. Work only on your slides: adding, moving or deleting slides and starting subagents is for me. Then `review_slide` each slide once and fix with the smallest tool (at most 2 rounds). If a write answers that a program is running on this deck, wait a moment and write again. Answer with one line per slide: id — done, or what is left.

- **Then** read the one-line answers and go on with step 8.

## The critic

One subagent with fresh eyes, started after all slides are written. It sees the result, not your plan, so give it no outline:

> You are reviewing a finished slide deck for <audience/purpose>, <slide count> slides, ids <ids>. The person wants: <profile line>. Read the design rules first: <how to read design.md>. Call `review_slide` on every slide, in order, and change nothing. Then name the 3 weakest slides, worst first, each with one line on what makes it weak (the point not visible at a glance, a diagram that shows without explaining, space left empty under the title or at the bottom, a cover that is only a headline, text too small for the back row, more on it than the point needs, out of line with the other slides, against the profile or the design rules) and one line on the fix, preferring what to remove over what to add. Then one line on the deck as a whole: does it look like one system? Answer with those lines only.
