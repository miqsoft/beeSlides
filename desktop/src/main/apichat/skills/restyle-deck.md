---
name: restyle-deck
description: Give an existing deck a new look (a glow-up, a new style, a template to follow) while keeping every slide's content — a family of slide types the slides are relinked to, then a polish pass.
---

Give the deck a new look. Keep its content exactly: every word, number, picture and the slide order stay; element ids stay (morph pairs, comments and links hang on them). Only how it looks changes. To merely fix alignment and spacing use polish-deck instead; for one slide, slide-designs.

1. **Read the deck.** `doc_info` (theme, slideTypes, designRules) and `outline` (each slide's current `slideType`). `review_slide` 3–4 representative slides (the cover, a typical content slide, the busiest one).
2. **One question.** Infer the profile from the deck (purpose, typical slide, decoration, motion — see build-deck step 2) and ask ONCE, in one message: the inferred profile for correction, and what should change ("calmer", "more visual", "more modern", "follow this template"). If the request already says enough, state your reading in one line and go on.
3. **Classify every slide.** A table in chat, one row per slide: id, its message (from its title or main text — unchanged), its evidence kind (the list in build-deck step 3), and the slide type it will follow. This is the deck's outline; content that would read better as another kind (five numbers in a text list → a chart or a table) is a suggestion in the table, not a change, unless the user asked for more visual slides.
4. **Pick the look with the user.** Take the most typical content slide and offer 2–3 clearly different looks for it with `propose_variants` (the slide's own content and ids in each; they differ in palette use, type treatment, title and takeaway placement — the things the whole deck will share). Ask the user to pick one in the app (its Use button) and to tell you which; you never learn the pick otherwise, and an unpicked set stays open over the canvas, where it covers your later `review_slide` screenshots. If they said to just do it, take the one closest to the profile and say so.
5. **Build the family** in the chosen look (build-deck step 4: theme via `deck_settings`, a parent type with the shared chrome, one child per evidence kind used, title/section/closing at top level).
   - **The deck already has slide types:** restyle them in place — `slide_html` read and write on each type, keeping its placeholder ids — so every linked slide follows at once. If one type carries slides of different evidence kinds (a single "content" type for everything), make it the parent and add a child per kind, then relink each slide to its kind's child — that is what lets a comparison and a one-result slide each get the arrangement they need.
   - **The deck has none, or slides that follow none:** create the family, then `slide_type` `{op:"relink", layoutId, slideId}` per slide. Read each result: `verdict` `partial` lists `floating` content that found no placeholder — note those slides for step 6.
   - The theme change recolours every element that refers to the palette; hex colours an earlier writer typed by hand do not follow — find them in step 6.
6. **Rework the slides that need it.** The floating ones, slides whose arrangement no longer fits their type, and slides with hand-typed colours or fonts outside the new look: `slide_html` read, change the arrangement and styling (never the text), write back with the same ids. More than 5 such slides: hand them to writers in consecutive runs with build-deck's writer block, adding "keep every word, number and element id; change only the arrangement and styling".
7. **Check.** Run the polish-deck pass over the whole deck (its consistency step compares slides of one type), start build-deck's critic for 8 or more slides and fix what it names, then `validate` once.
8. **Report** in two or three lines: the new look in one line, slides relinked or reworked, anything left (content that did not fit and why, suggestions from step 3).
