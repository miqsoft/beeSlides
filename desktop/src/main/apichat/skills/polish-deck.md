---
name: polish-deck
description: Design-review every slide of the deck and fix layout, hierarchy and consistency without changing its look — big decks are split across parallel subagents.
---

Run a polish pass over the whole deck. Keep the content and message of every slide and the deck's look (palette, typefaces, slide types); fix presentation only. To change the look use restyle-deck instead.

1. Call `doc_info` and `outline`. List the deck slides (skip hidden ones only if the user said so). If the user's request names slides or a range, restrict the pass to those. Note the profile: `doc_info` `designRules.profile` if present, else infer it from the deck in one line (purpose, typical slide, decoration, motion — see build-deck step 2). It decides what counts as a fix: a calm conference deck stays calm.
2. **Split the work.** With 4 or fewer slides do them yourself, one after another. With more, split the slides into consecutive batches of about 3 and give each batch to a subagent with `task`, issuing the `task` calls together in one turn so they run in parallel (at most 4 run at once; start the rest once those return). Every batch is a disjoint set of slide ids. Each prompt must be self-contained, for example:

   > You are polishing slides <ids> of the open slide deck (deck title: <title>, slide size <w>x<h>, slide types <…>). Profile: <one line>. For each slide, in order: call `review_slide` once; look at the screenshot and the element list; fix crowding, misalignment, unbalanced whitespace, inconsistent sizes/colours, text that wraps badly or overflows, text too small to read from the back row (under 18px on a slide meant to be presented), with the smallest tool; when a slide holds more than its point needs, move detail into the speaker notes or suggest splitting the slide rather than shrinking type (`update_element` for one element, `elements` for several or for moves; `slide_html` read/write only to restructure). After a write, handle any `LAYOUT` banner and call `check_layout` until clean (at most 3 rounds). Review again after your fixes (at most 2 polish rounds per slide). Do not change the wording or the message, the palette, the typefaces or the slide's type; add no animation, icon or effect the profile rules out; do not touch other slides, do not call `review_slide` on any slide not listed. Keep the deck's side margins (`--bs-margin`), palette and typefaces. Icons come only from the `icons` tool (the user's icon library); never draw icon SVG. Finish with a short report: per slide, what you changed and anything still open.

   Screenshots go through the one shared editor canvas, so they are taken one at a time automatically; that is expected.
3. When the subagents are back (or after your own slides), check **consistency across the deck** yourself with `outline` and a few `get_slide` `view:"summary"` calls: slides of the same slide type put the title, takeaway and footer at the same frames and sizes; the same accent colour; footers and page numbers alike. Fix differences with `elements` `{op:"edit"}`.
4. Check the deck against the design rules (`read_reference("design.md")`), filtered by the profile: numbers that should be a chart, consecutive slides that should share ids and `morph` (motion subtle or expressive only), speaker notes, lists of concepts or steps that would read faster with an icon per item (decoration icons only). Offer these as suggestions instead of redesigning unless the user asked for them. If many slides share a problem that only a new look fixes, suggest restyle-deck.
5. Run `validate` once. Then answer in a few lines: slides changed, remaining issues, suggestions.
