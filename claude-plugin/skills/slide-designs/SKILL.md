---
name: slide-designs
description: Propose 3 clearly different designs for a slide; the user compares them with the current slide and picks one.
---

_In this plugin: `task` is the Agent tool (subagents), and `read_reference("agents.md")` means reading `reference/agents.md` of the BeeSlides plugin, two folders up from this skill's base directory (`../../reference/agents.md`)._

Offer the user design options for one slide. They see your designs side by side with the slide as it is and pick one, keep the slide, or decide later. Nothing changes until they pick.

1. **Which slide.** The one the user names, else the slide they have open (the selection digest says which). Only one set of designs can wait for a pick at a time, so do ONE slide per call; for several slides, do the first and tell the user to say when they want the next.
2. **Understand it.** `slide_html` `{op:"read", slideId}` gives the slide as HTML; `review_slide` shows how it looks. Keep its content and message: the same title, points, numbers and pictures (reuse `<img src="element:<id>">` and the ids from the read).
3. **Design three real alternatives** (2–6 if the user asked for a number). They must differ in layout and emphasis, not only in colour. Start from what the slide has to show (its evidence kind, as in build-deck step 3) and offer different treatments of it that fit the deck: keep the title, takeaway and footer where the deck's slide types put them, and vary the content area, for example: cards in a row · one big number or statement with the rest small · picture or chart on one side, text on the other · a timeline or steps · a table. Stay within the deck's profile (`doc_info` `designRules.profile`, else what the deck shows: a calm deck gets no glows or motion). An alternative that would need a slide type the deck lacks says so in its note. Unless the user asked for something else, the set holds: the current form arranged differently, the other evidence form (table ↔ chart, diagram ↔ list, one figure ↔ small multiples), and the simplest version that still carries the point (the fewest elements, nothing under the deck's smallest type size). Write them all yourself in this one call; never start a subagent per design. Use the deck's theme variables (`--bs-accent`, `--bs-font`, `--bs-margin` …), keep content inside the side margins, at most two typefaces. Write each as HTML + CSS exactly as for `slide_html` write; keep the ids of elements that stay, so animations, links and comments survive.
4. **Propose them** in ONE call: `propose_variants` `{slideId, variants:[{label, note, html, css}, …]}`. `label` is a few words ("Three cards"); `note` one line on what the design does differently ("Leads with the 40% figure"). If the result lists a dropped design or notes, fix and propose again only if something important was lost.
5. **Show and tell.** Outside the app (Claude Code with the BeeSlides plugin), call `variants` `{op:"previews", slideId}` right after, so the designs show in the BeeSlides pane with a button each. Tell the user in one line that the designs are ready to compare — in the app, or in the pane — and that they can also answer with the number. Do not wait, poll or re-check the slide: when they come back, `variants` `{op:"status"}` says what they picked (or kept); if they answer with a number, `variants` `{op:"pick", slideId, index}` uses it. When they tell you, and the deck has other slides of the same evidence kind, offer in one line to give them the same treatment.
