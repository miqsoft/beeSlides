---
name: build-deck
description: Plan and build a new deck (or a run of new slides) from a topic or source material — profile, outline, a look the user picks, a family of slide types, one reference slide per type, then the slides (big decks in parallel), a check, and alternatives for the slides where a choice matters.
---

_In this plugin: `task` is the Agent tool (subagents), and `read_reference("agents.md")` means reading `reference/agents.md` of the BeeSlides plugin, two folders up from this skill's base directory (`../../reference/agents.md`)._

Build the deck the user asked for. Work in this order and keep the user informed in one short line per phase. This skill is for new decks and new runs of slides: to give an existing deck a new look use restyle-deck, to fix one up use polish-deck, for one slide use slide-designs or a direct edit.

1. **Look at what exists.** Outside the app (Claude Code with the BeeSlides plugin), when the user names a deck file or no deck is open, call `open_deck` with its path first (`create:true` for a new deck); `doc_info` then names the file and says `background` when no BeeSlides window shows it. Call `doc_info` (title, size, theme, slideTypes, designRules) and `outline`. Read the "Make a GREAT deck" section of the guide once: `read_reference("agents.md")` — skip it if you already know it.
2. **Profile — what the deck is for.** If `doc_info` has `designRules.profile`, use it. When adding slides to a deck that has content, infer it from the deck and never ask. For a new deck, ask ONCE, in one message, with a proposed answer for each question taken from the request, and say "change what is wrong, or say go":
   - purpose: conference talk · lecture · meeting · pitch · for reading;
   - length: minutes × pace → slide count (≈ 1 slide/min for a talk, ≈ 0.5 for a lecture or meeting), plus backup slides; for reading, a slide count;
   - typical slide: mostly text · text + small visual · balanced · visual + one-line takeaway · visual only;
   - visuals: does the user have figures or photos (files to attach)? decoration: plain · icons · imagery;
   - content that needs its own slide type: equations, code, tables, timeline, quotes, references;
   - motion: none · subtle (fades, morph) · expressive;
   - simplicity: minimal · clean · rich (how much one slide may hold; a pitch is minimal, a talk or lecture clean, a deck for reading rich);
   - existing look: a template or .pptx to follow, or none.
   Skip the question when the request already answers it or the user said to just do it; then state the profile in one line instead. The profile sets the budgets: the typical slide decides how much text a slide carries (visual + takeaway = a title plus one takeaway sentence; balanced = up to 3 short points; mostly text = up to 5), motion decides which `fx` you may use (none: no animations or transitions beyond a plain fade; subtle: fades and morph; expressive: anything), decoration decides icons and imagery (plain: neither).
   The purpose sets the tone. A conference talk, lecture, meeting or deck for reading **states and shows; it does not sell**: titles are claims the evidence supports, in plain words (no superlatives, no drama); a number never stands alone — it sits next to what it is compared with (the baseline, the other methods, last year) and says where it comes from (n, the test set, the source), which usually makes it a chart or a table; at most ONE large number in the whole deck, for the main result, and no count-up. Hero numbers, count-ups and one-word panels are pitch devices.
   **Density.** The slide carries the point; the speaker notes carry the detail. Per slide, at most (minimal / clean / rich): 4 / 7 / 10 text blocks, 1 / 4 / 8 boxes holding text, 3 / 4 / 6 items in one row, grid or list. On a slide meant to be presented, no text is smaller than 18px and body text is at least 24px (on 1280×720; scale with the slide size); for reading, 14px. Every fact the audience does not need to see the point goes into the notes or a backup slide. A diagram node or a box holds ONE text (its name); what it means goes into a caption under the diagram or into the notes, never a second label in every box. Group with space and alignment first, a rule second, a box last: never a box around a single text, never a box in a box. Over budget means split the slide, use a table, or move detail out — never shrink the type. Under budget is fine, but balance it: the content fills the content area or sits centred in it, never crammed into its top third with the rest empty — grow the chart or diagram, or centre the block.
3. **Outline before slides.** Write a numbered outline in chat, grouped by section, one row per slide: its message (the one sentence the audience should take away — this becomes the title or takeaway), its **evidence kind** and its material (which figure, which numbers). Evidence kinds: title · section · closing · statement (one sentence, big) · one-result (one figure + takeaway) · comparison (two side by side, aligned) · detail (a figure with an inset or callouts) · overview (3–4 small multiples) · number (one key figure beside what it is compared with; a hero-size number only in a pitch) · process (steps / flow / sequence component) · table (exact values) · list (3–5 points) · equation · code · quote. Choose the kind from what the slide must show, never for variety's sake; a series of slides showing the same kind of thing shares one kind on purpose (it reads as a series and morphs), but do not put more than 3 unrelated slides of one kind in a row. Keep to what the material supports; no filler slides. Where the form is genuinely open — a table or a chart, one figure or small multiples, a diagram or a list — write both in the row, your pick first ("table · or: scatter of F1 against time"), in at most 3 rows; the user's answer to the outline settles them, and without an answer your pick stands. **Decks over 10 slides: wait for the user's OK** on the outline (unless they said to just do it).
4. **Set the look once: a family of slide types.** The look comes from, in this order: what the user asked for, the deck's own look (a template, slide types of its own, a theme someone set), else the profile. With a look of its own, do not invent another: reuse its slide types and add only the kinds it lacks, as children of its parent type.
   **Without a look of its own, let the user choose it** (decks over 5 slides, unless they said to just do it): write the outline's most typical content slide in 2–3 clearly different looks with ONE `propose_variants` call on that slide (add it now, or reuse the deck's empty first slide; it stays and becomes that outline row, so count it in step 5). The looks differ in what the whole deck will share — light or dark, how the accent is used, the type treatment, where title and takeaway sit — never only in colour, and all stay within the profile. Ask the user to pick one: in the app with its Use button, or — outside the app (Claude Code with the BeeSlides plugin) — call `variants` `{op:"previews", slideId}` right after, so the designs show in the BeeSlides pane, where they pick or answer with the number. Learn the pick from `variants` `{op:"status"}` instead of asking; an unpicked set stays open over the canvas. The variants may use literal colours; once picked, set the theme to them and build the family in that look.
   Then build the family:
   - **A type scale, fixed once:** title, body, label (and one hero size, pitch only) — e.g. 40 / 28 / 20 px for a talk. Every slide uses only these sizes, never in-between ones; state the scale in chat and give it to every writer.
   - **Theme** with `deck_settings` `{op:"theme"}`: a palette (background, text, one accent, a second only if needed) and at most two typefaces, chosen for the purpose — a conference talk or lecture is calm and readable (light or dark, flat, square corners, no shadows or gradients); a pitch may be bold. Effects such as glows, frosted glass or gradient text only with motion expressive or decoration imagery. Set `{op:"size"}` if asked.
   - **A parent type** ("Base", `create_slide_type` mode blank) holding what every content slide shares, written with `slide_html` write on the type: the title (`data-role="title"`), the takeaway line if the profile has one, the footer or page number (`{{page}}`). These positions never change between types — that is what makes the deck look like one system. HTML cannot mark a slot, so then turn each slot into a placeholder in ONE call — `elements` `{op:"edit", slideId:<type id>, changes:[{id:"title", placeholder:"Title", html:""}, …]}` — or every slide shows the type's sample text; `doc_info` then lists them under the type's `placeholders`.
   - **One child per evidence kind the outline uses** (`create_slide_type` mode parent from Base, then `slide_html` write on the child for what it adds, e.g. the caption line of one-result, the two column headings of comparison, its slots made placeholders the same way). Title, section and closing get their own top-level types. Check the family once with `doc_info`: every type lists its placeholders and a `contentArea`. Only the content area differs between children.
5. **Reference slides.** Add every slide the outline needs in ONE call before filling any: `deck` `{op:"add", after, slideType, count, names}` (one call per run of slides that share a type is fine) returns the new ids in order; reuse empty placeholder slides that `outline` already lists first. Then write the FIRST slide of each slide type yourself and `review_slide` it: these are the references every other slide of that type copies. **Decks over 10 slides: tell the user which slides are the references, ask them to look at them in the app, and wait for an OK** before writing the rest (unless they said to just do it).
6. **Write the remaining slides.** With 5 or fewer left, write them yourself, copying the reference of their type. With more, hand them to writers (see "Writers" below).
   - **If the `execute` tool is available (Code Mode)**, write your own slides as one `execute` program (a few for a long deck) instead of one call per slide: write each one's HTML from shared functions, set notes, transitions and each slide's animations, and return the ids and warnings. The deck API is in the beeslides server's instructions; `api_search` only for what they leave out. The rules below still apply inside the program.
   - **Write each slide as HTML**: `slide_html` `{op:"write", slideId, html, css}`. Lay it out with ordinary CSS (flexbox, grid, padding, gap) — the app lays it out in the browser and turns every box into an element, so you never compute a frame. Fill the slide type's placeholders by giving your elements their ids and placing them at the placeholder's frame (`#<id>{position:absolute; left:<x>px; top:<y>px; width:<w>px}` keeps the family's look), and lay the rest out inside its `contentArea`; keep to the theme variables (`--bs-accent`, `--bs-font`, `--bs-margin` …, never a hex value of your own) and a whole text element in one typeface. Give every element an `id`; the same `id` on the next slide plus `transition:"morph"` morphs (only with motion subtle or expressive). Diagrams are components — `<div id data-component="steps|sequence|cards|compare|flow">` with the data as JSON (`slide_html` `op:"help"`): far fewer tokens than hand-made boxes and arrows, the deck's colours, and `data-active` / `data-show` step through them slide by slide. Tables are `<table>`, charts `<div data-chart='{"preset":"bar","option":{…}}'>`, code `<pre>`, pictures `<img src="data:…">`; `op:"help"` lists the rest. The result lists anything it left out, so read it.
   - Animations, within the profile's motion: set a slide's `fx` in ONE `elements` `{op:"edit", changes:[{id, fx}, …]}` call, not one `update_element` per element.
   - Changes: small ones with `update_element` / `elements`; to restructure a slide, `slide_html` `{op:"read"}`, edit the HTML, write it back (ids keep animations and links).
   - Icons, only with decoration icons: `icons` `{op:"search", query}` with one short noun per concept, then `{op:"insert", slideId, ref, x, y, size}`; one size for every icon on a slide. Never draw icon SVG yourself; if the library is not set up, say so in the report and use simple shapes.
   - A figure the user has not supplied yet: a clearly marked placeholder box ("Figure: <what it shows>") in the slot, never an invented chart of made-up numbers.
   - Put speaker notes on each slide with `deck` `{op:"notes", slideId, text}`; set transitions and sections with `deck` too (`op:"help"` lists the ops).
7. **Check the deck as a whole.**
   - For every slide you wrote yourself, `review_slide` once and fix what the screenshot or the layout findings show with the smallest verb (at most 2 polish rounds per slide). Do not re-review slides a writer reviewed unless its line says something is left.
   - Consistency: with `outline` and a few `get_slide` `view:"summary"` calls, check that slides of one type put the title, takeaway and footer at the same frames and sizes; fix differences with `update_element` / `set_frame`.
   - Profile: no animation, icon or effect the profile rules out; no more than 3 unrelated slides of one type in a row.
   - With 8 or more slides, start ONE critic (below) and fix the slides it names, at most 2 rounds each.
   - Run `validate` once for the whole deck; delete leftover empty slides you added with `deck` `{op:"delete"}` (never the user's slides unless they asked).
8. **Offer alternatives where a choice matters.** Name the slides where another design is most likely better — the main result, and the critic's weakest slides even after your fixes, at most 4 — and offer in one line: "I can show 2–3 alternatives for slides 8, 9 and 12 to compare in the app; want them?". Only on a yes, one slide at a time (one set can wait for a pick at a time): write all its alternatives yourself in ONE `propose_variants` call — never a subagent per alternative, they would each re-read what you already know. The set always holds: the current form arranged differently, the other evidence form (table ↔ chart, diagram ↔ list, one figure ↔ small multiples), and the simplest version that still carries the point (the fewest elements). Keep the content, the slide type's title and footer, and the ids of elements that stay. Ask the user to pick (in the app, or in the BeeSlides pane after `variants` `{op:"previews"}`), read the pick with `variants` `{op:"status"}`, then go on with the next slide. After each pick, if the deck has other slides of the same evidence kind, offer in one line to give them the same treatment ("Slide 7 is a table too — make it as lean?"). With "just do it", skip this step and mention the slides in the report.
9. **Report** in two or three lines: what was built, the profile in one line, what was left for the user (figures to drop in, anything `deck` help lists as not available yet), nothing else.

## Writers: plan once, write in parallel

When more than 5 slides are left after the references and you can start subagents (`task` in the built-in chat, the Agent tool in Claude Code — writers can run on a faster model, e.g. sonnet), split the writing; the time a deck takes is mostly the writing, and writers work at the same time.

- **Batches are consecutive runs** of 2–4 slides, ideally one section each, so morph pairs and series stay with one writer. Batches are disjoint; start every writer in ONE message so they run together.
- **Each prompt is self-contained** — a writer knows nothing else. Copy this block and fill in the <…> parts, leaving out nothing:

  > You are writing slides <ids> of an open slide deck (deck title: <title>, size <w>x<h>). Profile: <one line: purpose, typical slide, decoration, motion>. Your slides, in order, with their outline rows: <id — slide type — evidence kind — message — material>. For each slide type you use, here is its reference slide; copy its title placement, takeaway, spacing, font sizes and colours exactly, and lay your content out inside the type's contentArea <[x,y,w,h]>: <type name: reference HTML and CSS from slide_html read>. Write each slide with `slide_html` write (or, if the `execute` tool exists, ONE program for all your slides). Use only the theme variables for colours; diagrams as `data-component` (steps, sequence, cards, compare, flow); ids unique per slide, the same id on consecutive slides for morph<, only if motion allows it>; no animation, icon or effect the profile rules out; a missing figure is a marked placeholder box, never invented data. Density: only the type scale's sizes (<title / body / label px>), nothing under <18>px; at most <n> text blocks and <n> boxes per slide; one text per box or diagram node; detail goes into the speaker notes; over budget, tell me instead of shrinking the type. Speaker notes with `deck` notes; animations in one `elements` edit per slide. Never add, move or delete slides, never touch slides that are not yours, never start subagents. Then `review_slide` each of your slides once and fix with the smallest verb (at most 2 rounds). If a write answers that a program is running on this deck, wait a moment and do it again. Answer with ONE line per slide: id — done, or what is left.

- **You finish:** read the one-line answers, then go on with step 7.

## The critic

One subagent with fresh eyes, started after all slides are written. It sees the result, not your plan — that is the point, so do not give it the outline. Prompt:

> You are reviewing a finished slide deck for <audience/purpose>, <slide count> slides, ids <ids>. The person wants: <profile line>. Call `review_slide` on every slide, in order. Change nothing. Then name the 3 weakest slides, worst first, each with one line on what makes it weak (the point not visible at a glance, text too small to read from the back row, more on it than the point needs, out of line with the other slides, against the profile — e.g. a pitch-style hero number in a scientific talk) and one line on the fix, preferring what to remove over what to add. Then one line on the deck as a whole: does it look like one system? Answer with those lines only.
